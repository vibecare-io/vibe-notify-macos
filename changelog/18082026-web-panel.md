# Web panel — a break you can play, watch or read

An alert can now embed a live web page beside its text and countdown, so a
break can *be* something — play a game, watch an exercise short, glance at a
page — instead of only describing one.

## What's new

`RichNotification.webPanel` puts a `WKWebView` in one column and the existing
rich chrome in the other: title, message, countdown ring, buttons, footnote,
all unchanged. It is a property of the existing model rather than a fourth
renderer, so every legibility rule, scrim strategy and button outcome already
in `RichNotificationView` applies to it untouched.

```swift
RichNotification(
  webPanel: WebPanel(
    url: URL(string: "https://www.youtube.com/shorts/eG51cFCbPZs")!,
    placement: .leading,
    widthFraction: 0.36,
    allowsAutoplay: true,   // starts muted; see below
    loops: true),
  title: "Rest your eyes",
  message: "Play until the ring finishes.",
  taskTimer: TaskTimer(duration: 60, unitLabel: "seconds", completionLabel: "Eyes rested"),
  mode: .interrupt)
```

### YouTube links are rewritten

`watch?v=`, `youtu.be`, `/shorts/` and `/live/` all become an embedded player,
keeping any `?t=` start offset in either spelling (`t=68`, `t=1m30s`). Shorts
especially need it: followed directly, a Short plays and then scrolls on to the
next one, handing the user an infinite feed at the moment the break was meant
to stop them looking at one.

### Two interaction changes when a panel is present

- **Click-anywhere-to-dismiss is suppressed.** Everywhere else it is a
  courtesy; with a game in the panel, one shot landing in the margin would
  cancel the break and explain nothing.
- **The countdown leads the rail** instead of following the text, because the
  rail is read against a panel that has already taken the eye.

## Autoplay, and the two things that block it

`allowsAutoplay` emits `autoplay=1`, and `startsMuted` (**on by default**)
emits `mute=1`. They are separate properties but related in one direction:

1. **Muted autoplay is the only kind browsers grant** without a user gesture.
   `allowsAutoplay` with `startsMuted: false` is refused by policy, and refused
   *silently* — a blocked autoplay is indistinguishable from a video waiting to
   be clicked.

2. **macOS Low Power Mode defeats autoplay entirely.** WebKit's
   `RequireUserGestureForVideoDueToLowPowerMode` requires a real click to start
   any video — muted or not, and whatever
   `mediaTypesRequiringUserActionForPlayback` is set to. No API lifts it, and
   nothing here detects it: the only thing that satisfies the gate is the user
   pressing play, which is the fallback anyway. The symptom is a video that
   loads and displays perfectly, shows its play button, and never starts.

## Two error codes worth recognising

Both were caused by *how the embed was loaded*, not by the video:

| Symptom | Cause |
|---|---|
| `Error 153 — video player configuration error` | No `Referer`/origin. A top-level navigation to `/embed/` carries none. |
| `Error 152 — this video is unavailable` | The wrapper document claimed the target's own origin. An embed is meant to be cross-origin. |

The player is loaded in an ordinary `<iframe>` inside a document whose origin is
a reserved `.invalid` host — third-party to the target, and unresolvable so it
cannot be mistaken for a real site or collide with one's cookies.
